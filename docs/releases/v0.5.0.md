# v0.5.0

Explicit signing APIs and conservative device/key capability profiles extend
the library while preserving the existing low-level `Sign` and `Authenticate`
wire behavior.

## Migration notes

- `MLDSASigner.Sign` now accepts only nil options and `crypto.Hash(0)`. Options
  that were previously ignored, including a nonzero hash or a custom zero-hash
  options type, return `ErrUnsupportedMLDSAOptions` before an APDU. Its input is
  the complete pure ML-DSA message with an empty context; signing a hash as a
  message does not implement HashML-DSA. Existing pure CSR/certificate callers
  using nil options remain supported.
- `ErrMLDSAOptionsUnsupported` remains an alias of
  `ErrUnsupportedMLDSAOptions`. `ValidateRSA` remains a wrapper for the more
  explicit `ValidateRSASignRequest`.
- Nil and typed-nil supported RSA options consistently return
  `ErrInvalidRSAParameters`; unimplemented schemes or hashes use
  `ErrUnsupportedRSAOptions`.
- `PublicKeyAlgorithmName` identifies named curves exactly. P-521 display
  changes from `ecdsa-521` to `eccp521`; other unknown EC curves use the curve
  name rather than a bit-count label. Consumers parsing CLI algorithm strings
  should account for this change and prefer typed key descriptors.

## Signing APIs

- `SignRSA`, `ValidateRSASignRequest` and `VerifyRSA` distinguish PKCS#1 v1.5
  named-hash digests, exact caller payloads and RSA-PSS. SHA-256/384/512 are
  implemented; MGF1 hash must explicitly equal the digest hash. PSS salt length
  zero means exactly zero, not Go's automatic-salt sentinel.
- `SignECDSA` and `ValidateECDSASignRequest` provide P-256/P-384 signing with
  standard digest-to-integer conversion and strict DER responses.
  `PrepareECDSADigest` includes off-card P-521 preparation without claiming a
  native device path.
- Invalid signature lengths and malformed/noncanonical ECDSA DER wrap
  `ErrInvalidSignatureResponse`. The private operation may already have
  completed; callers must not automatically retry it.
- Signing APIs validate parameters and response shape but do not verify the
  signature against the expected public key or perform implicit PIN
  verification. Consumers must authorize the operation and verify its result.

## Capability profiles

- Signing profiles bind exact key and scheme parameters, slot restrictions,
  input/result/transport limits and evidence. Typed result encodings and
  machine-readable reason constants are exported.
- Pure helpers construct `SigningKey`, slot evidence with an explicit
  caller-supplied freshness decision, and a concrete RSA signing request.
  Certificates and stored templates never become authoritative metadata.
- RSA PKCS#1 v1.5 and exact zero-salt PSS profiles are deterministic. Positive
  PSS salt profiles use host CSPRNG and do not guarantee determinism.
- YubiKey model names follow the documented ykman 5.9.2 snapshot contract,
  including `YubiKey 5A`; firmware and PIV applet versions remain distinct.
- Live `supported` matching requires current authoritative key metadata.
  NEO, YubiKey 4 and YubiKey 5 before firmware 5.3 remain `unknown` under this
  contract. SafeNet signing profiles remain qualification-pending. Static
  device profiles do not establish the current private key or authorize use.

## Scope and qualification

The existing CLI retains its `none`/`sha256` signing interface; use the explicit
library APIs for the new schemes. See the [API guide](../signing.md) and
[hardware qualification matrix](../signing-qualification.md) for exact supported
device, firmware, slot and parameter combinations. P-521, secp256k1 and Ed448
native paths remain pending; no universal PIV support is implied.
